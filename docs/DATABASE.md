# DocuAI Database

- Engine: PostgreSQL 16
- ORM / migrations: Prisma 6 (`backend/prisma/schema.prisma`,
  `backend/prisma/migrations/`)
- Connection: `DATABASE_URL`
- Test database: `TEST_DATABASE_URL` (`docuai_test`), created automatically by
  `docker/postgres/init/01-create-test-db.sh` on first start of the Postgres
  volume.

## Migration policy

- Migrations are created with `npx prisma migrate dev --name <name>` in
  development and applied with `npx prisma migrate deploy` everywhere else
  (the backend container runs `migrate deploy` on start).
- Applied migrations are immutable. Never edit a migration that has been
  committed; add a new one.
- `npx prisma migrate status` must report the database as up to date.

Phase 0 established the Prisma toolchain and migration workflow; its two
`*system_config*` tables are not referenced by the application or the Prisma
schema any more but are left in place because applied migrations are
immutable. Phase 1 introduced the first application models; Phase 2 and
Phase 3 are strictly additive (new enums, new tables, foreign keys to
existing tables). The Phase 3 migration was generated by Prisma and then
hand-edited only to **remove** the `DROP TABLE` statements Prisma proposed
for the legacy `system_config` tables, so it never touches existing data.

## Schema

```
users 1 ──── N refresh_tokens
users 1 ──── N folders        folders 1 ──── N folders (parent_id, tree)
users 1 ──── N documents      folders 1 ──── N documents (folder_id, nullable)
users 1 ──── N ocr_jobs       documents 1 ──── N ocr_jobs    ocr_jobs 1 ──── N ocr_pages
```

### Enum `UserStatus`

`ACTIVE` | `SUSPENDED` | `DELETED`

- `ACTIVE` – normal account.
- `SUSPENDED` – login and refresh are refused (`AUTH_ACCOUNT_SUSPENDED`);
  data is retained. Reversible.
- `DELETED` – soft-deleted; authentication is refused
  (`AUTH_ACCOUNT_DELETED`). The row is kept so uniqueness, audit trails and
  future data-retention jobs keep working. Hard deletion is a later-phase
  concern.

### Table `refresh_tokens` (model `RefreshToken`)

One row per device session.

| Column | Type | Constraints | Notes |
| ------ | ---- | ----------- | ----- |
| `id` | `uuid` | PK | referred to as "session id" in security events |
| `user_id` | `uuid` | FK → `users.id`, not null | |
| `token_hash` | `char(64)` | unique, not null | HMAC-SHA256 (hex) of the opaque token, keyed with `JWT_REFRESH_SECRET`. **The raw token is never stored.** |
| `expires_at` | `timestamptz` | not null | `created_at + JWT_REFRESH_EXPIRES_IN` |
| `revoked_at` | `timestamptz` | nullable | set on logout, rotation, expiry-on-use or security revocation. Rows are **kept** after revocation so a revoked token presented again can be recognised as reuse |
| `device_name` | `varchar(100)` | nullable | client-supplied label (`deviceName`) |
| `user_agent` | `varchar(255)` | nullable | truncated `User-Agent` header |
| `ip_address` | `varchar(45)` | nullable | client IP as seen by the API (`TRUST_PROXY` controls `X-Forwarded-For` handling) |
| `created_at` | `timestamptz` | not null, default `now()` | |
| `updated_at` | `timestamptz` | not null | |

Indexes:

| Index | Purpose |
| ----- | ------- |
| `refresh_tokens_token_hash_key (token_hash)` unique | lookup on every refresh/logout |
| `refresh_tokens_user_id_idx (user_id)` | FK support, "sessions of a user" |
| `refresh_tokens_user_id_revoked_at_idx (user_id, revoked_at)` | "active sessions of a user" (`revoked_at IS NULL`), bulk revocation on reuse detection |
| `refresh_tokens_expires_at_idx (expires_at)` | future clean-up job for expired rows |

#### Cascade behaviour

`refresh_tokens.user_id` is declared `ON DELETE CASCADE ON UPDATE CASCADE`.
Physically deleting a `users` row therefore removes every session of that
user. This is intentional: a session must never outlive its owner. Note that
the application does **not** hard-delete users in Phase 1 — account removal is
modelled as `status = DELETED` plus revocation of all refresh tokens, so the
cascade only matters for operational clean-up or future GDPR erasure jobs.

#### Privacy notes on session metadata

`device_name`, `user_agent` and `ip_address` exist so a later phase can show
users a "where you're signed in" list and so security events can be
investigated. They are personal data:

- They are only ever written at session creation; they are never returned by
  any Phase 1 endpoint.
- `user_agent` is truncated to 255 characters; `ip_address` is stored as
  presented (IPv4 or IPv6, ≤ 45 chars).
- Revoked and expired rows are retained for reuse detection. A retention /
  pruning job (e.g. delete rows revoked or expired for more than N days) is
  planned for a later phase and should be part of the data-retention policy.
- Security events log `userId`, `sessionId`, `requestId` and `ip`, never the
  email, password, token or token hash.

### Enum `DocumentStatus`

`DRAFT` | `UPLOADING` | `READY` | `PROCESSING` | `FAILED` | `DELETED`

- `DRAFT` – metadata only, no upload requested.
- `UPLOADING` – an upload URL was issued; `storage_key`, `mime_type`,
  `file_size` and `original_name` hold the client's declaration.
- `READY` – the object was verified in storage; `file_size`/`mime_type` are
  the verified values. Only `READY` documents can be downloaded.
- `PROCESSING` – reserved for future pipelines; still never set by Phase 2 or
  Phase 3 code. OCR progress lives on `ocr_jobs.status`, so a document stays
  `READY` (and downloadable) while it is being OCR'd.
- `FAILED` – `upload-complete` found an object that contradicts the
  declaration; the object was removed and a new upload URL is required.
- `DELETED` – soft-deleted (always together with `deleted_at`). Excluded from
  every query; there is no recovery path in Phase 2.

### Table `folders` (model `Folder`)

Per-user folder tree (adjacency list).

| Column | Type | Constraints | Notes |
| ------ | ---- | ----------- | ----- |
| `id` | `uuid` | PK | |
| `user_id` | `uuid` | FK → `users.id` `ON DELETE RESTRICT`, not null | owner; every query is scoped by it |
| `name` | `varchar(100)` | not null | trimmed, no control characters; names are not unique (same as a filesystem would be too restrictive for scans) |
| `parent_id` | `uuid` | FK → `folders.id` `ON DELETE RESTRICT`, nullable | `NULL` = root folder |
| `created_at` | `timestamptz` | not null, default `now()` | |
| `updated_at` | `timestamptz` | not null | Prisma `@updatedAt` |

Indexes:

| Index | Purpose |
| ----- | ------- |
| `folders_user_id_idx (user_id)` | "all folders of a user", FK support |
| `folders_user_id_parent_id_idx (user_id, parent_id)` | children of a folder / root folders of a user |

Both FKs are `RESTRICT` on purpose: a user row cannot be physically removed
while it owns folders, and a folder cannot disappear while children point at
it. The application deletes folders inside a transaction that first moves the
children (`parent_id` → the deleted folder's parent) and the documents
(`folder_id` → `NULL`), so the constraint is a safety net, not a code path.
Cycle and depth prevention (max 10 levels) are enforced in the service with a
recursive CTE under a per-user advisory lock; the schema itself only
guarantees referential integrity.

#### Cascade behaviour

- `documents.folder_id` is `ON DELETE SET NULL`: if a folder row is ever
  removed outside the application path, its documents fall back to the root
  instead of being deleted. Documents are never cascaded away.
- `documents.user_id` and `folders.user_id` are `ON DELETE RESTRICT`. User
  removal is modelled as `users.status = DELETED` (Phase 1); physical erasure
  of a user must first run the storage clean-up and delete documents/folders
  explicitly — the constraint prevents orphaned objects in the bucket.

#### Soft delete and storage objects

Soft-deleting a document keeps the row **and** the object in the bucket.
Every application query filters `deleted_at IS NULL`, so the document and
its file are unreachable through the API immediately. Retention/purge
(delete the object, then the row) is a later-phase job; the
`(user_id, deleted_at)` index and the retained `storage_key` exist for it.
Soft-deleting a document does **not** touch its `ocr_jobs`/`ocr_pages`; they
become unreachable through the API because every OCR query first resolves the
document with the Phase 2 ownership + `deleted_at IS NULL` filter. A job that
is still queued when its document is deleted ends as `CANCELLED`
(`OCR_DOCUMENT_UNAVAILABLE`) the next time a worker picks it up.

### Enum `OcrJobStatus`

`QUEUED` | `PROCESSING` | `COMPLETED` | `PARTIAL` | `FAILED` | `CANCELLED`

- `QUEUED` – row created and (normally) an entry pushed to the BullMQ queue.
  The database row is the source of truth; a missing queue entry is repaired
  by the reconciler.
- `PROCESSING` – claimed by a worker; `heartbeat_at` is refreshed after every
  page. `PROCESSING` with a stale heartbeat (`OCR_STALE_JOB_MS`) means the
  worker died and the job is recoverable.
- `COMPLETED` – every page processed, none failed.
- `PARTIAL` – every page attempted, at least one `FAILED` page (e.g. a page
  timed out). Retryable through `POST …/ocr/retry`.
- `FAILED` – job-level failure (`error_code` set). Retryable unless the code
  is permanent (`OCR_UNSUPPORTED_FILE_TYPE`, `OCR_INVALID_FILE`,
  `OCR_FILE_TOO_LARGE`, `OCR_PAGE_LIMIT_EXCEEDED`, `OCR_PAGE_TOO_LARGE`,
  `OCR_UNSUPPORTED_LANGUAGE`, `OCR_DOCUMENT_UNAVAILABLE`).
- `CANCELLED` – the document was deleted or is no longer `READY` before the
  job ran. Terminal, not retryable.

Terminal rows (`COMPLETED`, `PARTIAL`, `FAILED`, `CANCELLED`) are never
mutated again; reprocessing or retrying creates a new job.

### Enum `OcrExtractionMethod`

`NATIVE_TEXT` | `OCR` | `MIXED`

Pages are `NATIVE_TEXT` (text layer read with `pdftotext`) or `OCR`
(rendered with `pdftoppm` / read directly for images and recognised by
Tesseract). The job-level value is `MIXED` when its pages used both.

### Enum `OcrPageStatus`

`COMPLETED` | `EMPTY` | `FAILED`

`EMPTY` is a successful page without recognisable text (blank scan); `FAILED`
carries an `error_code` and no text.

crash or a BullMQ duplicate delivery overwrites rather than duplicates.

#### Cascade behaviour

- `ocr_pages.ocr_job_id` cascades: pages have no meaning without their job.
- `ocr_jobs.document_id` / `ocr_jobs.user_id` are `RESTRICT`, consistent with
  `documents`/`folders`: a future hard-delete/retention job must purge OCR
  history explicitly and deliberately.

### Consistency guarantees

- **Document state changes** are conditional updates
  (`UPDATE documents SET … WHERE id = $1 AND user_id = $2 AND deleted_at IS NULL AND status IN (…) [AND storage_key = $3]`)
  with `count = 1` required. Concurrent `upload-url` / `upload-complete` /
  `DELETE` calls therefore serialise on the row and a stale request cannot
  overwrite a newer state (e.g. complete an upload whose key was replaced, or
  undo a delete).
- **Folder hierarchy mutations** run in a transaction holding
  `pg_advisory_xact_lock(2001, hashtext(user_id))`, so two concurrent moves
  by the same user are serialised and cannot create a cycle between them.
  Folder deletion (move documents → root, promote children → parent, delete
  row) is atomic.
- **OCR job creation** runs inside a transaction holding
  `pg_advisory_xact_lock(3001, hashtext(document_id))`, so two concurrent
  `POST /documents/:id/ocr` calls cannot both create an active job for the
  same document; the second one sees the first job and returns it.
- **OCR job claiming** is a single conditional
  `UPDATE ocr_jobs SET status = 'PROCESSING', attempt_count = attempt_count + 1, … WHERE id = $1 AND (status = 'QUEUED' OR (status = 'PROCESSING' AND heartbeat_at < now() - stale))`
  with `count = 1` required, so a duplicate BullMQ delivery or a second
  worker finds nothing to claim. Terminal rows are never claimed. Page
  results are upserted on `(ocr_job_id, page_number)`, counters are updated
  with a conditional `UPDATE … WHERE status = 'PROCESSING'`, and the final
  status is derived from the persisted pages, so a job interrupted after
  page *n* resumes at page *n + 1* without duplicating rows.
- **Registration** runs `users.insert` and the first `refresh_tokens.insert`
  in one transaction; a duplicate email surfaces as a unique-violation
  (`P2002`) which is mapped to `409 AUTH_EMAIL_ALREADY_EXISTS`.
- **Rotation** is a transaction containing a conditional
  `UPDATE refresh_tokens SET revoked_at = now() WHERE id = $1 AND revoked_at IS NULL`
  followed by the insert of the replacement row. Under READ COMMITTED,
  concurrent requests presenting the same token serialise on the row lock and
  exactly one sees `count = 1`; every other one sees `count = 0` and is
  handled as reuse (all active sessions of the user are revoked).
